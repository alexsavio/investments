- **R3 — Double-taxation credit: taxable-net base + 2-dp rate.** Status: TODO
  Two coupled corrections. (a) The rate limb currently uses **gross** foreign income; TEAC RG 00/08643/2023 (20-10-2025, unificación de criterio, binding per LGT art. 239.8) requires **rentas netas** "una vez deducidos los gastos y compensadas las rentas": base = the foreign income as actually integrated into the base liquidable — net of pro-rated deductible fees (Común) and zeroed to the extent compensation wiped the group it sits in. Restore the dropped `taxable_eur` limb from the original design. (b) LIRPF art. 80.2 / NF art. 76.2 "expresado con dos decimales" is operative: round the average rate to two decimals **as a percentage** (fraction to 4 dp) before multiplying — AEAT Manual Renta 2025 cap. 18 example: 16,60% × 6.000 = 996. Tests: Común year where a prior-year RCM ledger wipes the foreign dividends' group → credit 0; the AEAT 996 vector; Gipuzkoa unchanged-gross case still passing (art. 91 wording, state doctrine filling a foral gap — cite both).
  Commit: `fix(spain-tax): base the double-taxation credit on taxed net income at the two-decimal rate`
- **R4 — Común compensation order per AEAT Manual cap. 12.** Status: ✅ Done (`8d5ed408`) — implemented **before** R3, because the credit's taxable-net base is evaluated after compensation and R3 has to read R4's corrected outputs.
  `compensate_savings_base` now runs Fase 1ª (current-year cross) → Fase 2ª-1º (own-group ledgers) → Fase 2ª-2º (prior-year leftovers cross), with a single per-group allowance measured on the **original** current-year positive and consumed across both cross steps. `LossLedger::apply`'s `cap` is live in Fase 2ª-2º; `LedgerApplication::merge` folds the two passes over the same ledger. `CompensationResult`/`SpanishTaxStatement` gain `prior_cross_offset_*`, with two new CSV summary rows. Manual example (+4,000 / −800 / 2,800 / 500) reproduces base **200** exactly, and a cap test proves the allowance is measured pre-absorption (500 vs the old 1,500). Gipuzkoa: `gipuzkoa_is_unchanged_by_the_two_phase_order` pins the same inputs at 1,200 with every cross figure zero, and all pre-existing Gipuzkoa unit + fixture assertions passed untouched.
  All three implemented behaviors are refuted for Común (Gipuzkoa unaffected): the current-year cross-offset must run FIRST (Fase 1ª), prior-year same-group ledgers attack the reduced remainder (Fase 2ª-1º), unabsorbed prior-year leftovers DO cross groups (Fase 2ª-2º), and the 25% cap is a **joint** cap on the **original unreduced** current-year positive, consumed across both cross-offset steps. Rewrite `compensate_savings_base`'s Común path accordingly (the `cap` parameter of `LossLedger::apply` becomes live). Primary test: the manual's own worked example — current GyP +4,000, current RCM −800, prior GyP 2,800, prior RCM 500 → base **200** (the current code yields 900). Also assert one-direction-per-year still holds where the manual implies it, and that Gipuzkoa results are bit-identical before/after.
  Commit: `fix(spain-tax): follow the AEAT two-phase compensation order for Territorio Común`
